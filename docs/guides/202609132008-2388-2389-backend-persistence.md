# Policy / Resource / 软件发布持久化（#2388 + #2389）

## 能力与 owner

三个独立 package 为 `rss-mdm-policy-postgres`、`rss-mdm-resource-postgres`、`rss-mdm-software-release-postgres`。它们只依赖对应核心与必要 RSS/PG，不读取其他业务表。`rss-mdm-app::software_publication` 负责映射、引用、服务身份、源目标、公开产物和成功审计。

所有 Store 借用宿主持有的同一个 `Arc<PgRuntime>`；宿主负责关闭。独立运行角色通过 verify-full TLS 连接，禁止 owner/superuser/BYPASSRLS/DDL/权限转授。构造 Store 校验精确 schema catalog、约束、索引、RLS 和有效权限。app 组合 admission 还拒绝无关业务表/序列/函数权限、schema CREATE、audit grant option 和宽松 audit tenant policy。`*_in` 校验 runtime owner/tenant，永不自行 commit；调用方必须处理业务拒绝并将外层 PG 错误返回给事务 owner。

Resource/Release 的 Outbox MessageId 使用原 RequestId 的固定长度 SHA-256 编码，以容纳核心允许的斜线等字符；业务回执和事件载荷保留完整原身份。

持久文档只支持当前格式，字段数量、闭合枚举、摘要和核心构造器共同校验；无历史兼容读取、path patch 或另外的 Outbox。

## Policy

`Request` 使用核心 RequestId，包含 expected_storage_revision、固定 as_of 和 Create / Transition / SelectTargets / ReplaceFacts / Replan。`execute/execute_in` 先核对原请求，再 CAS；同请求改内容、时间或预期 revision 拒绝。相同语义的新请求可无变化，但原文和回执仍保留。

storage_revision 统一保护状态、完整目标、分配引用、事实和当前计划。核心 Policy revision 不替代存储 CAS。有效输入变化使计划过时；只有显式 Replan 能重新安装，A→B→A 不让旧计划自动恢复有效。PlanId 仍由原核心语义输入决定；不可变计划只保存确定性决策输入，安装/刷新来源由独立请求回执记录。Aggregate::current_plan_request 指向当前安装；plan(policy, request) 恢复该请求的准确 as_of、RequestId 和共用 PlanId，不把首次计算误作当前安装。

ReplaceFacts 只更新已存在的完整 execution key，输入必须是执行 owner 已归并的当前权威事实；不接受原始异步回执排序。旧版本事实只更新旧行；取消/取代意图不伪造 Cancelled、卸载或效果回滚。N10 不解析 Group/Scope、不派发。

`get`、`version`、`target_snapshot`、`plan`、`operation` 和 `execution_facts` 提供恢复/查询。事实查询返回 FactPage(records, next)，下一页将 next 原样作为 after；limit 为 1–1000。单次规划最多 10,000 条事实/目标，文档最多 64 MiB；超限拒绝，历史不会被静默截断。该上限不是容量 SLO，扩大规模需执行 owner 的明确摘要/分页契约。

## Resource 与完整版本发布

Resource 的 Version 内容单独存为不可变记录，聚合只保存生命周期引用。`Resource::snapshot/restore` 校验租户、资源、kind、唯一 Active 和状态结构。ResourceStore 提供 execute、version、get、operation 及借用事务入口；Archive 只能在伴随事务中执行。app 先锁版本并检查所有持久候选引用；被历史候选引用的版本也不归档。

一个 Candidate 是完整平台包版本。SoftwareIdentity 为 source/package/version/platform，Content 的 VariantContent 持有全部 architecture/variant 和产物闭包。V2 摘要直接替换旧单 variant 输入；没有旧发布接口或格式 shim。

ReleaseStore 保存候选、验证/审批、原请求/回执和每次发布尝试历史。相同软件版本的描述、manifest、variant 和产物不可变；源配置快照独立绑定审批。重放只返回历史 receipt，不返回 Publish，不回退当前状态。

## app 使用顺序

1. 以受控进程配置构造 ArtifactReader、具名 RingSources(test、pilot、production) 和 ServiceActors，再 `PublicationService::connect`。物理源全局独占，绑定唯一逻辑 source 与固定 ring；不允许另一个 tenant 或逻辑别名共享同一外部命名空间。发布者与审批者必须分离，所有 actor 匹配 tenant；本入口不接收外部管理 HTTP 身份声明。
2. ResourceStore 创建资源及冻结版本。CandidateInput 明确资源版本、预期资源 revision、候选/请求身份、固定时间和 Submission。
3. `create_candidate` 在事务外读取产物，事务内重验资源和完整平台集合，原子保存候选、引用、软件版本 authority 与成功审计。
4. `validate` → `approve` → `authorize` 使用 ServiceRequest(id、expected_revision、as_of)。每环重新验证审批，后环要求前环已 Published；保留原请求用于重放。
5. 授权事务固定 PublicationId、attempt、目标字节/摘要、Brew base/target commit 和源互斥槽。提交后 `publish` 才记录可能已调用并执行一次外部写。
6. `reconcile` 只读取原目标并记录核心结果；外部成功、本地失败/未知时继续使用原 PublicationId/attempt。`candidate` 和 ReleaseStore::operation/original_request/attempt_history 可查证结果。

只有信息预检阶段可证明未发送写请求的失败才记录 NotApplied、释放互斥，并允许 `retry` 创建同 PublicationId 的下一次尝试。POST 阶段超时和未知结果只能继续对账，不按 404 重试。

WinGet 按完整 package/version 互斥，只 POST，不通过 PUT 覆写冲突。写身份使用 x-functions-key，读取信息与完整版本核对真实源及批准内容。Resource variant key 通过 `winget_variant(Query)` 得到，包含 installer type、scope 和显式 installer ID/无 ID；必须覆盖全部 installer。

Brew 每环使用独立专用 bare Tap，同一 Tap 的 main 修改串行。Cask 映射完整架构集合；Formula 映射全部 Bottle、源码产物与调用方明确声明的依赖快照/产物。依赖声明由受控调用方 attestation，当前不发现依赖或运行 Ruby。Bottle URL 对照固定上游 Filename URL 编码（rebuild=0）；所有实际读取对象均验证长度与 SHA-256。

## 撤回与未知

withdraw 使用调用方稳定 ServiceRequest 先隔离候选，关闭新授权；尚未调用的发布可在同一受控事务证明 NotApplied。已可能调用且结果未知时撤回保持 Pending，禁止先删除后让迟到 POST 重现。

撤回请求和调用目标分开保存，目标只可 INSERT。WinGet 仅删除精确版本；Brew 在最新已核实 head 上删除仍由该发布持有的定义，保留其他包和旧 commit。旧版本已经被新版本取代时撤回为 no-op，不回退分支。

`reconcile_withdrawal` 只查询已调用的原目标，不发起新的删除；尚未调用的撤回由显式 `withdraw` 继续。WinGet 1.0 没有操作查询：确认 204 加版本缺失可完成；DELETE 回包丢失后即使看到 404，仍保留 Pending 和互斥，不自动重发或释放。信息预检明确未发送 DELETE 时，以成功审计记录该事实，允许显式 withdraw 再调用同一固定目标；仅查询的 reconcile_withdrawal 不重试。需要源 owner 提供终止/对账能力后独立接入，当前不提供未经证明的强制成功入口。Brew 可用已进入分支历史的删除 commit 对账。

旧 commit、公开产物与历史引用都保留。本期无 GC、缓存即时撤销、自动回退或终端卸载。重新发布相同版本须先查清全部旧尝试并完成撤回，再建新候选、重新审批，字节仍须相同。

## 产物与权限

产物仅为已上传的公开 CDN/S3 稳定 HTTPS 对象。匿名 GET，不发送 Authorization、Cookie 或源专用头；拒绝内嵌身份、query/fragment、重定向和隐式代理。origin/IP/CA 仅来自受控进程配置（私有 CA/IP 用于受控 T2，生产 CDN 可使用系统公开根），Submission 不能扩展该允许集合。显式批准 origin/IP/CA，保留证书和主机名验证；读取为流式、有界时间/长度并校验 SHA-256。公开对象可以被持有链接的人读取，RLS 只保护资源、审批、来源、调用和审计元数据。

无上传、私有下载授权、签名 URL 或通用存储 provider。下载授权以后独立设计，不以假 credential reference 代表匿名访问。

## 迁移与验证

外部管理员先创建已有 mdm_owner 等基线角色，再执行 `crates/app/schema/software-publication-roles.sql`；新角色默认 NOLOGIN，凭据/登录角色由部署 owner 最小授权，不写入源码。`rss-mdm migrate` 以 mdm_owner 执行十四个具名、固定摘要单元，包含 RSS messaging、三个 adapter 和 app 组装；运行角色不执行 DDL。RSS relay 角色属于 PG 集群级身份；MDM 与独立 Identity 使用分离的 PG 实例，避免 MDM migrator 的角色成员关系破坏 Identity 对 relay 的安全校验。生产源部署不属于本批 T2。

```sh
make test
make t2-backend
make t2-publication
# 已提交且 clean 后，以固定源码 SHA 逐包消费
make backend-consumers
MDM_IDENTITY_CANDIDATE=/absolute/approved-identity-candidate make ci
```

backend-t2 使用固定摘要 PG、verify-full TLS、隔离角色和真实 COMMIT 回包丢失代理；publication-t2 使用真实 PG/HTTPS、有状态 WinGet 兼容协议 fixture 和 bare Git。缺依赖或未执行必要测试明确失败。独立消费者按 default/no-default 获取固定 Git SHA，分别核对普通/构建闭包、实际 feature tree、独立 lock/target 和真实 PG 行为，不能由测试直接依赖补齐 adapter features。

结果绑定 PR 受测 SHA、RSS pin、lock 和实际命令输出；源码消费不是 registry 发布，协议 fixture 不是生产源部署，T1/T2 不是端侧 T3。没有独立性能 SLO，本项 benchmark gate 不适用。
